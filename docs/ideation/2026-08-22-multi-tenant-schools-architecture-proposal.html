SafeRide architecture proposal · 22 August 2026

Multi-Tenant Schools

Add a customer tenant above schools, keep operations inside one active school, and enforce isolation through a server-resolved session context, scoped DAOs, relational constraints, and a database backstop.

1. Outcome and recommendation

Recommendation: use a separate tenants table above live_schools. A tenant is the customer/legal workspace and owns the fleet; a school is an operating site with its own students, routes, runs, gate, and bell times. Staff requests operate inside one active school. Kuumbai enters an audited support context instead of impersonating a customer identity.

The proposed tenant_id is necessary, but it is not sufficient by itself. Isolation fails if one list query forgets its predicate, if a relationship connects records from different tenants, or if an authorization claim stays valid after a role is removed. The security boundary therefore needs four cooperating layers:

  1. A server-owned session context with active tenant, active school, actor, and effective permissions.
  2. DAO interfaces that cannot be called without an explicit trusted scope.
  3. Database constraints that reject cross-tenant and cross-school relationships.
  4. PostgreSQL row-level security as a final backstop before the second tenant is enabled.

Constraints and assumptions

  • Production remains one FastAPI/Lambda deployment and one PostgreSQL database; isolation is logical, not deployment-per-customer.
  • Msingi Bora is the only live customer, its existing school is the canonical first school, and all current production operational data belongs to it. The migration aborts if preflight disproves this.
  • SafeRide's existing bearer-session authentication and driver PIN flow remain; Firebase continues to serve push messaging only.
  • A tenant may own several schools, but ordinary staff use one tenant and one active school at a time in this release.
  • Buses and drivers belong to a tenant and may be assigned to at most one school at a time; school operations remain unmerged.
  • Parents remain global identities whose access follows explicit child links across tenant boundaries.
  • Automated owner invitations require a production email transport and verified sender that do not yet exist in this repository.

Tenant

Customer boundary, contact details, lifecycle state, tenant owner, aggregate health, fleet.

School

Operating boundary, gate and bell times, director/coordinator assignments, students, routes, runs.

Provider

Exists outside tenants; provisions, audits, and enters one selected tenant/school support context.

Predicates + DB policy
  • The client never supplies a trusted tenant_id or school_id for ordinary CRUD. Create operations stamp them from RequestContext.
  • A switch endpoint necessarily receives a requested school ID. It validates tenant ownership and membership, updates the server-side session, and returns the accepted context. Other endpoints ignore or reject scope fields in payloads.
  • Membership removal is effective on the next request because the context resolver checks active membership instead of trusting a long-lived role claim.
  • Cross-tenant reads use scoped predicates and return 404, avoiding confirmation that the foreign record exists. Permission failures inside the correct context return 403.

DAO rule

Do not add an optional tenant_id=None argument to existing DAOs. Create scoped repositories that require a validated scope at construction or on every method. Keep global/provider aggregate DAOs and parent/driver DAOs separate so there is no generic “unscoped admin” escape hatch.

Constraint pattern

  • Add unique keys such as (id, tenant_id) or (id, tenant_id, school_id) on owned records.
  • Use composite foreign keys for route-to-bus, student-to-route, run-to-route/bus/driver, plan-to-school, and all snapshot/join tables.
  • Index the exact scoping prefix used by lists, for example (tenant_id, school_id, created_at DESC).
  • Use database triggers or serialized transactions for the “last owner” and “last director” invariants; an application count followed by delete is race-prone.
  • Reject reassignment of a bus or driver while an active run or incompatible school-owned route references it.

Database backstop

RLS is worth adding because the data concerns children and the current regression originated from losing database-enforced scope. It should be staged after scoped application queries, not used as a substitute for them:

  1. Create a non-owner runtime database role; keep schema migrations on an owner role. The current runtime credentials appear to use the database owner/master path, which can bypass ordinary RLS.
  2. Open a transaction and use SET LOCAL for actor/mode/tenant/school so pooled connections cannot retain one request's scope.
  3. Apply and force policies on tenant/school data. Parent and driver policies use their dedicated relationships, not staff active-school rules.
  4. Expose provider health through a narrow aggregate query/function. Never set “no tenant” to mean “all rows.”

6. Primary journeys and UI states

Provider creates tenant

  1. Provider enters customer name and first-owner email.
  2. API creates tenant, pending invitation, and email-outbox row in one transaction.
  3. Provider sees pending delivery and can resend or revoke.
  4. Owner follows the single-use link and receives owner membership. A new user sets profile/password; an existing SafeRide identity keeps its password and gains the membership without duplication.
  5. Owner lands in resumable first-school setup.

Owner creates first school

  1. Create school name, contact details, gate, and bell times.
  2. Automatically make the owner a director of that school.
  3. Set it as the server session's active school.
  4. Reuse existing fleet, driver, student, route, and plan screens in guided order.

Owner switches school

  1. Cancel in-flight client queries and show a neutral switching state.
  2. POST the requested school to the context endpoint.
  3. Server validates access and stores the accepted active school.
  4. Clear school-scoped query caches and fetch the new school.
  5. Never render old and new school data together.

Provider assists safely

  1. Provider chooses a tenant, school, and support reason.
  2. Server creates a support session and active scoped context.
  3. Console shows a persistent support banner and explicit exit.
  4. All reads and writes are scoped and privately audited with the provider actor.
  5. School-facing activity displays SafeRide.

7. Implementation phases

Each phase is separately reviewable and reversible at the code level. Do not activate another tenant before all gates through Phase 7 pass.

Phase 0 — Inventory and test harness

  • Generate an inventory from FastAPI's registered routes and classify each as public, provider-global, tenant-scoped, school-scoped, driver-scoped, or parent-linked.
  • Add two tenants with two schools and deliberately overlapping names to local/integration fixtures.
  • Create an isolation coverage manifest test that fails when a new non-public endpoint lacks a scope classification/test.
  • Capture current production-safe preflight SQL for counts, nullable school ownership, orphan relationships, duplicate emails, and the existing admin identity without printing sensitive values.

Gate: every API route and persistent table has an explicit scope owner before schema work begins.

Phase 1 — Additive tenancy schema

  • Add tenant, membership, invitation, support-session, provider-audit, and email-outbox tables.
  • Add nullable tenant/school scope columns and supporting indexes to existing live-model tables.
  • Add active context columns to auth_sessions.
  • Do not change current runtime behavior yet; this migration must remain compatible with the existing production code.

Gate: current certification suite passes unchanged against the expanded schema.

Phase 2 — Msingi Bora backfill and integrity checks

  • Abort unless production preflight matches the documented one-customer assumptions.
  • Create Msingi Bora tenant #1 and attach the existing school.
  • Attach all buses and drivers to the tenant; attach all school-owned and derived records to the canonical Msingi Bora school.
  • Convert the existing admin identity into tenant owner and school director without changing its password.
  • Backfill active context lazily for existing sessions with exactly one eligible tenant/school.
  • Validate row counts, relationship counts, null scope, and cross-scope anomaly queries. Persist the evidence.

Gate: before/after counts match, all required scope is populated, and the existing admin still signs in.

Phase 3 — Context resolver and permission engine

  • Implement RequestContext, membership resolution, active-school switching, and action-level permissions.
  • Replace singular role assumptions in auth responses while maintaining a temporary compatibility mapping for existing frontend routes.
  • Implement immediate revocation and last-owner/director invariants transactionally.
  • Add dedicated provider, parent, and driver context paths.

Gate: auth tests cover stale sessions, revoked membership, provider support, parent cross-tenant links, and driver assignment.

Phase 4 — Scoped DAO and API conversion

  • Convert endpoint families in narrow slices: schools/fleet → accounts/students → routes/plans → runs/incidents → notifications/push.
  • For each slice, require scope at the DAO boundary, stamp scope on create, predicate every read/write, validate relationships, and add two-tenant tests before moving on.
  • Remove driver self-signup; retain parent self-signup and global email linking.
  • Return non-enumerating not-found responses for foreign tenant/school IDs.

Gate: the endpoint manifest proves every data-returning and mutating route has an isolation classification and passing coverage.

Phase 5 — Provider, invitation, staff, and switching UI

  • Add provider tenant health/list, create-tenant, invitation state, and audited support entry/exit.
  • Add activation page and resumable first-school setup.
  • Add active-school display/switcher, tenant settings, staff management, coordinator capability hiding, and support banner.
  • Include tenant and school keys in query-cache keys; cancel and clear scoped queries during switching.
  • Replace the hard-coded school identity in AdminLayout.tsx.

Gate: Playwright proves provider onboarding, owner setup, school switching with no stale data, coordinator restrictions, and support-mode labeling/audit.

Phase 6 — Composite constraints and non-null enforcement

  • Add same-tenant/same-school composite foreign keys as NOT VALID where useful, validate them, then make required scope columns non-null.
  • Add indexes matching tenant/school list and time-order predicates.
  • Reject future orphan scope in the database, including bulk import and plan materialization paths.

Gate: deliberate cross-tenant SQL relationship writes fail and the full application suite remains green.

Phase 7 — RLS hardening and tenant #2 readiness

  • Separate migration-owner and runtime database roles.
  • Set request context transaction-locally on pooled connections; add forced RLS policies for tenant/school data.
  • Implement narrow provider-health aggregation without an unscoped record API.
  • Run the full isolation, browser, migration, and operational certification against a clean two-tenant environment.

Gate: only after this phase may Kuumbai send the first production invitation to tenant #2.

Definition of done

  • Every registered route has a declared scope and a corresponding automated isolation test.
  • No staff DAO can execute without a validated scope.
  • No required operational row has a null tenant or school after migration.
  • Database constraints reject cross-boundary relationships.
  • RLS runs under a non-owner runtime role and survives pooled-connection tests.
  • Msingi Bora data counts and the existing login are preserved.
  • Provider invite, setup, support, audit, and neutral actor labeling pass end to end.
  • School switching has browser proof showing no stale data.
  • Coordinator direct-request tests prove destructive actions are refused.
  • The second tenant remains disabled until all gates pass.

9. Production rollout and rollback

  1. Preflight: take a recoverable database snapshot; record table counts and anomaly queries; confirm the canonical Msingi Bora school and admin mapping.
  2. Expand release: deploy additive schema only. Current application remains compatible.
  3. Backfill release: create tenant #1, populate scope and memberships, and verify. Do not onboard tenant #2.
  4. Scoped application release: deploy server enforcement, then frontend context/provider/setup features. Existing one-school sessions default safely.
  5. Constraint/RLS release: enforce integrity and database backstop; rerun full certification.
  6. Pilot verification: Msingi Bora director signs in with existing credentials; separate coordinator account performs the daily flow; Kuumbai enters and exits support mode.
  7. Tenant #2: only now create and send the first production owner invitation.
Rollback boundary: additive tables/columns should remain in place during rollback. Before tenant #2 has data, code can roll back to the preceding one-tenant version if necessary. After any second-tenant data exists, an unscoped application version must never be redeployed; rollback may target only a previously certified tenant-aware version. This is the point of no return.

11. Remaining decisions before implementation

The product architecture is settled. These operational/compliance decisions should be answered before their corresponding implementation slices, and the first two before invitation/staff work starts.
  1. Which production transactional-email transport and verified sender identity will send owner invitations?
  2. Should school directors/coordinators retain the original temporary-password creation flow, or reuse the email invitation flow?
  3. What are the tenant/school deletion, retention, export, and recovery rules? Until decided, destructive provider controls stay disabled.
  4. How long are provider audit events retained, and must Kuumbai be able to export them?

Explicit non-goals for this release

  • Ordinary staff tenant switching or membership in several tenants through the UI.
  • Merged operational maps, rosters, or run views across schools or tenants.
  • Buses or drivers serving several schools concurrently.
  • Self-service tenant signup, billing, subscription enforcement, branding, organizations above tenants, or multi-campus school records.
  • Firebase Authentication migration.
  • True user impersonation.
